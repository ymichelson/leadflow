# LeadFlow

שלב ב' של פרויקט הבית: פרוסה אנכית שמקבלת פנייה מטופס אתר, מסווגת אותה,
מונעת כפילויות וכותבת אותה ל-HubSpot.

**דמו חי:** [טופס יצירת קשר](https://web-production-b50b3.up.railway.app/) ·
[תצוגת מערכת](https://web-production-b50b3.up.railway.app/ops)

## מה בניתי

```text
טופס אתר
  -> שמירה מקומית והחזרת 202
  -> תהליך רקע
  -> נרמול וסיווג ב-Gemini
  -> סף ביטחון ובדיקת אדם במקרה הצורך
  -> חיפוש איש קשר קיים ב-HubSpot
  -> יצירת איש קשר או עדכון שלו + הוספת note
  -> ניסיון נוסף אם הכתיבה ל-CRM נכשלת
```

בחרתי במסלול הזה מפני שהוא תנאי לניתוב ולמדידת זמני תגובה: קודם צריך להוכיח
שפנייה נקלטת ונכתבת באופן אמין. זו אינה כל המערכת שתוארה בשלב א'.

## איך לבדוק את הדמו

1. שולחים פנייה מהטופס.
2. מתקבל אישור מיד לאחר שהפנייה נשמרה, לפני הקריאות ל-Gemini ול-HubSpot.
3. בתצוגת המערכת רואים את הסיווג, ציון הביטחון ותוצאת הכתיבה ל-CRM.
4. שליחה נוספת עם אותו אימייל או טלפון מעדכנת את אותו איש קשר ומוסיפה note,
   במקום ליצור רשומה כפולה.

תצוגת המערכת מציגה עד 30 אירועים מאז עליית השרת האחרונה. היא נועדה לדמו
ואינה היסטוריה תפעולית; ההיסטוריה המלאה נמצאת ב-HubSpot.

## מה אמיתי ומה ניסיוני

### עובד ואומת

- טופס ו-API ציבוריים.
- שמירה ב-SQLite לפני החזרת `202 Accepted`.
- מזהה ייחודי לכל שליחה, כדי שניסיון חוזר לא ייצור עבודה כפולה.
- התאוששות אוטומטית מעבודה שנקטעה לאחר הפעלה מחדש של השרת.
- סיווג אמיתי ב-Gemini שמוחזר במבנה קבוע ונבדק שוב בקוד.
- חיפוש, יצירה, עדכון וכתיבת note ב-HubSpot אמיתי.
- נרמול מספרי טלפון ומניעת כפילות לפי טלפון או אימייל.
- תור עמיד לניסיונות חוזרים; פנייה שלא נכתבה אינה נמחקת.
- 62 בדיקות אוטומטיות ו-CI בכל push.

בדיקת המסווג כוללת 16 פניות סינתטיות. לאחר שהוגדר כלל ברור בין `support`
ל-`existing_customer`, ריצה אמיתית אחת מול Gemini הסתיימה ב-16/16 וללא
טעות בטוחה. `--dry-run` משתמש במסווג מזויף ובודק רק את מנגנון המדידה. זו
בדיקת פיתוח קטנה, לא מדידת איכות על נתוני לקוח אמיתיים.

### קיים כאב-טיפוס

- שיוך round-robin נשמר בשדה `leadflow_assigned_rep`; הוא אינו
  `hubspot_owner_id` אמיתי.
- בדיקת זמן התגובה משתמשת באיש קשר שנשאר `NEW` כהערכה. היא אינה מודדת
  תגובה אמיתית לכל פנייה.
- קיים webhook ל-WhatsApp עם אימות חתימה, אך הוא לא אומת מול חשבון Meta פעיל.
- `/ops` הוא חלון לדמו ולא מסך עבודה לצוות המכירות.

### לא נבנה

- ערוץ אימייל.
- דוח שבועי שנשלח למנכ"ל.
- התראות שמגיעות לבעלים תפעולי.
- מענה אוטומטי מלא ללקוח.

## החלטות חשובות

- הדפדפן מקבל `202` רק אחרי שמירה. המשמעות היא "הפנייה התקבלה באחריות",
  לא "כל העיבוד הסתיים".
- פלט AI מחוץ לערכים המותרים או מתחת לסף הביטחון עובר לבדיקת אדם.
- לאחר הצלחה נמחקים ממסד הקליטה הטקסט ופרטי הקשר. נשארים רק מזהה, טביעת
  תוכן וסטטוס, ו-HubSpot נשאר מקור האמת.
- המערכת מעדיפה ניסיון נוסף על אובדן פנייה. במקרה נדיר של קריסה בדיוק אחרי
  כתיבת note, הניסיון הבא עלול ליצור note כפול.
- SQLite ותהליך הרקע מתאימים לשרת אחד. הדמו ב-Railway משתמש בדיסק קבוע;
  עבודה על כמה שרתים דורשת Postgres או תור משימות מנוהל.

## הרצה מקומית

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements-dev.txt
cp .env.example .env
uvicorn main:app --reload
```

כתובות מקומיות:

- `http://localhost:8000/` — טופס.
- `http://localhost:8000/ops` — תצוגת דמו.
- `http://localhost:8000/status` — מצב JSON.
- `http://localhost:8000/health` — health check.

בדיקות:

```bash
pytest -q
python eval.py --dry-run
```

`--dry-run` בודק את מנגנון המדידה עם classifier מזויף. ריצת מודל אמיתית:

```bash
python eval.py --delay 13
```

## משתני סביבה עיקריים

| משתנה | תפקיד |
|---|---|
| `GEMINI_API_KEY` | סיווג ב-Gemini |
| `AI_PROVIDER` | `gemini` או `anthropic` |
| `ANTHROPIC_API_KEY` | נדרש רק אם בוחרים `anthropic` |
| `HUBSPOT_TOKEN` | HubSpot Private App token |
| `STATE_DB` | נתיב ל-SQLite; ב-Railway מוגדר תחת `/data` |
| `CONFIDENCE_THRESHOLD` | סף לבדיקת אדם; ברירת מחדל 70 |
| `REPS` | שמות הנציגים למדיניות ההדגמה |
| `SLA_HOURS` | יעד זמן התגובה בשעות עבודה (השם הטכני של ההגדרה) |
| `APP_SECRET` | חובה להפעלת webhook של WhatsApp |

Scopes נדרשים ב-HubSpot:

- `crm.objects.contacts.read`
- `crm.objects.contacts.write`
- `crm.schemas.contacts.write`
- `crm.objects.notes.write`

אין להעלות את `.env` ל-Git או לשתף את ה-private app token.

## מבנה הפרויקט

- `main.py` — FastAPI, הטופס, `/ops`, `/status` וקבלת הודעות WhatsApp.
- `intake.py` — שמירת פניות, מניעת עיבוד כפול ותהליך רקע.
- `pipeline.py` — נרמול, סיווג והעברה ל-CRM.
- `classify.py` — חיבור ל-Gemini ול-Claude ובדיקת הפלט שלהם.
- `crm.py` — HubSpot, מניעת כפילויות, notes וניסיונות חוזרים.
- `business_hours.py`, `sla.py` — חישוב שעות עבודה ובדיקת זמן תגובה ניסיונית.
- `eval.py` — ערכת בדיקה למסווג.
- `test_leadflow.py` — בדיקות אוטומטיות.
